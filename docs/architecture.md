# Architecture

On macOS, the launcher sets the Foundation process name before initializing Tauri/AppKit so an unbundled development executable appears as `25小厨` in the Dock. `Info.plist` also supplies `CFBundleDisplayName` for embedded development metadata and packaged bundles; the build script tracks that file for recompilation.

```text
Trusted launcher (React, main)
   │ fixed Tauri commands
   ▼
Rust service controller ── bundled Node.js ── SillyTavern :selected-port
   │                                             │
   └─ persistent application data                └─ tavern webview (no native capabilities)
```

`service.rs` owns the child process. Startup reads validated launcher-settings.json (default port 25252; legacy mode fields are ignored), reserves the explicitly selected IPv4 wildcard port, prepares a versioned writable runtime, starts a fixed entry point with the selected port and fixed IPv4 listen arguments and enforced private-network whitelisting, then waits for HTTP readiness and a live child. Failure cleans up only that child. Address-in-use errors are surfaced without switching ports, including an EADDRINUSE or the pinned upstream IPv4 port-conflict diagnostic in the fresh child log after the reservation-to-bind race. Other failures are surfaced. User data and config live outside versioned runtimes. Port settings are read-only while running; saving requires an idle service mutex and no live owned child, so startup cannot race a settings write.

`lib.rs` exposes a small command surface and embeds a separate child webview in the main window (Tauri multiwebview feature). The React host synchronizes its bounds and hides it when navigating to launcher pages, preserving the tavern session. Capabilities and native command guards identify the trusted launcher webview, not the shared OS window. Its main-frame navigation is restricted to the current owned loopback origin, including the selected port. A stale child webview is recreated when the origin changes. The renderer cannot choose executable paths or arbitrary arguments.

`runtime.lock.json` is the source of truth for upstream provenance; update the matching Rust revision constant and displayed version in the same PR. macOS ships one Universal installer, with both architectures in the Rust launcher and Node.js executable. Windows ships one x64 installer. The source archive is checked before extraction. npm dependencies are installed from upstream's lockfile with lifecycle scripts disabled.

Node.js archives are downloaded from the official distribution and verified against committed SHA-256 values. macOS combines the two official Node executables with lipo and ad-hoc signs the result. The pinned SillyTavern dependencies are JS/WASM-only; preparation rejects native modules until an explicit cross-architecture strategy is added. The release job replaces the development signature with Developer ID signing (including Node JIT entitlements), refreshes the Node hash, notarizes and staples both app and DMG, and checks the extracted updater archive.

Website and desktop remain independent repositories. The website reads a small public release manifest; installers and updater artifacts reside in immutable R2 object keys behind a Pages Functions custom subdomain on Workers Free. The bucket remains private; the gateway performs at most two R2 reads per request and has no origin fallback. Uploads stop before the bucket exceeds 9 GB; this is not an account-wide billing cap. No production host credentials are stored here.

`updates.rs` serializes update checks/installations, accepts commands only from the trusted launcher, and uses the pinned Tauri updater to verify payload signatures and signed versions. Downloads complete before the owned service is stopped. The process controller blocks new starts during installation. Update errors release operation guards, and user data remains outside the installed application.

The release publisher uploads and verifies all R2 objects before publishing `updater.json` with separate macOS CPU aliases pointing to the same Universal archive and one Windows x64 installer. Both release manifests use no-store caching. Manual downloads remain exactly two installers. Private signing credentials live in protected GitHub environments, never in source or logs.

The website proxies only the small latest/updater manifests from R2 with no-store caching and redirects versioned download paths to the custom domain. Existing updater endpoints remain compatible. The original disk-backed Caddy configuration is retained until R2 migration is complete. See [R2 rollout](r2-distribution.md).

The download gateway uses Pages advanced mode, with all paths handled by the Function and no installer static assets. The main domain keeps its external authoritative DNS; only the download CNAME targets the Pages project. Preview environments have no R2 binding and downloads disabled.

The launcher uses a viewport-height shell with independently scrollable navigation and launcher pages. Service controls remain in the sidebar; an About entry opens a native HTML modal dialog containing branding, versions and updates. The update panel stays mounted while the dialog is closed to preserve automatic checks and download state. Opening About hides the child tavern webview and closing it restores its visibility without changing the selected page or session; the active tavern host fills the remaining width and height without launcher headers or footers. The initial window is a compact 860 × 640 logical pixels. A running transition requests native window maximization (not fullscreen) through a launcher-only command. A stopped transition restores 860 × 640, bounded by the current monitor work area (subject to the existing 720 × 620 minimum), unless the window remains maximized or fullscreen. Fullscreen/maximized choices are preserved; polling and navigation between pages do not repeatedly resize the window.

`ChefMascot.tsx` owns the launcher-only SVG mascot. Pointer coordinates drive bounded gaze and expression springs without React renders per frame; visibility, unmount and reduced-motion changes stop animation appropriately. The chef artwork and implementation are original; interaction concepts were referenced from [grokbot-web](https://github.com/Coiggahou2002/grokbot-web), with no imported code, geometry or dependency.

In production, the launcher GuidePanel fetches only `https://www.chef25.com/api/tavern-guide` when opened or refreshed (8-second timeout). It validates structured plain text, renders through React escaping, and displays content only after a successful API response. No bundled content or localStorage cache is used; opening or refreshing clears content while loading, and failed requests show a retry prompt. The CSP permits only that additional HTTPS path; remote content receives no native capability or executable HTML. Development uses the Vite same-origin proxy to the loopback content service on port 25254. Plain HTTPS URLs render as escaped external links; loading and failure states center within the remaining content area. Publishing text requires no desktop release after this feature is installed. The independently deployed website content service owns editor authentication and persistence.

`storage.rs` provides launcher-only, read-only directory listing and bounded UTF-8 previews (128 KiB). Commands derive the root from app_data_dir, reject non-relative paths and link/reparse-point traversal, and verify canonical containment. File content renders as escaped text, never HTML. Browsing runs on blocking workers and does not require the tavern service.

Reset is a launcher-only fixed command. It requires an exact confirmation phrase, holds the service mutex, rejects running services and update installation, and reserves the configured port to reject possible orphaned services. It deletes only fixed owned data entries (the saved launch port in `launcher-settings.json` is kept), rejects linked root ancestors, and never follows nested symlinks during deletion. The UI requires the service to be stopped and uses a modal text confirmation; partial failures are surfaced.

Closing the main window prevents native close and minimizes it to the Dock/taskbar without shutting down or cancelling the owned service. A second launch restores and focuses the existing window. The settings page has no exit section; system quit remains available. ExitRequested and Exit run idempotent shutdown. Shutdown sets a permanent cancellation flag before acquiring the child mutex, interrupts readiness polling, and rejects queued starts. Startup rechecks cancellation after runtime preparation. Forced process termination remains outside this normal-exit guarantee; unknown port owners are never killed.

The running sidebar exposes locally generated QR codes and copyable LAN URLs from private IPv4 interfaces, with interface selection and no-address feedback. The native embedded tavern continues to use loopback. Service startup listens on 0.0.0.0 and forces upstream whitelist mode, with process-local SILLYTAVERN_WHITELIST allowing loopback and RFC1918 IPv4 ranges; Docker host expansion is disabled. Persistent config and user authentication are preserved. The UI explains trusted same-network access; public access is separately opt-in through the protected OpenFrp ingress described below. Stopping removes mobile access information and terminates the same owned server.

`backup.rs` implements ZIP format version 1 with a marker and an explicit content allowlist (`data`, config, launcher settings, logs). Launcher-only commands own native file selection; no renderer-supplied arbitrary filesystem write path or additional tavern capability is exposed. Export writes a private temporary ZIP before publishing to the selected destination outside app data. Import rejects traversal, symlinks, special files, case collisions, malformed settings, unsupported markers, and archives over 100,000 entries / 10 GiB unpacked; CRC is checked while extracting to a same-volume staging directory. Old owned entries are moved aside only after full validation; rename failures roll back, retaining recovery folders if rollback fails. Runtime copies are cleared. Process mutex and port reservation serialize both transfers against starts, resets, settings changes and updater installation. Exact confirmation phrases are enforced in both UI and Rust. Replacement is rollback-capable for ordinary I/O failures, not a crash-atomic multi-directory transaction; interruptions may require manual recovery from the retained staging/previous directories.

The Contact Developer entry is a subdued text button inside About; closing its modal returns to About. The Contact Developer modal hides the tavern child webview while open, embeds the support QR locally, and opens the fixed project Issues URL through a launcher-only native command with no renderer-supplied URL or shell input.

`remote.rs` validates a deliberately restricted INI subset and downloads the pinned, SHA-256-verified official OpenFrp client on demand. `service.rs` owns both gateway and FRPC children under the service/remote lock order, and cleans them on normal stop, update, shutdown or observed child exit. `native/remote-gateway.mjs` is compiled into the launcher with `include_str!` and runs using the bundled Node executable; passwords arrive through stdin, and requests are authenticated before streaming to the fixed owned tavern port. Proxy/forwarding headers are stripped and upgrades rejected. The gateway binds an ephemeral loopback port; this is an internal ingress port, not a change to the configured tavern port. Imported local targets are overwritten and dangerous FRPC features rejected. The frontend never supplies executable paths or arbitrary shell arguments. Only launcher commands may start/stop/read remote access or open the fixed provider console.

The switch is session-only. Configurations are not persisted or backed up; a private temporary INI exists while FRPC runs. Public HTTPS readiness is verified without sending the password, requiring the unique local gateway marker and an authentication challenge. Later status reports process liveness only. Forced launcher termination remains outside the normal child-cleanup guarantee. The optional downloaded client is separate from the bundled runtime; cross-platform download hashes are pinned, but Windows execution and a real OpenFrp account remain acceptance work.

Transient operation feedback uses the shared `message` API and one `MessageViewport` at the React root. A manual popover places notifications in the top layer; the viewport moves into the active modal to stay within its accessible, interactive boundary. Messages auto-dismiss (4 seconds, 6.5 seconds for errors), pause on hover/focus, support manual dismissal, and deduplicate active messages with a three-message limit. Polling failures notify once until recovery. Loading indicators, empty states and destructive-action explanations remain contextual.
When the separate native tavern webview is visible, messages stay at the top of the launcher sidebar to avoid being covered by that native surface; other pages and modal dialogs use the window top center.

Shared launcher UI lives in `src/components/`: `Button` / `IconButton` retain native attributes and default to non-submit buttons; forms opt into `type="submit"`. `Dialog` synchronizes controlled state with native modal visibility and keeps children mounted, while `ConfirmationDialog` shares phrase validation, busy dismissal protection and action layout for reset/import/export. Business commands and concurrency guards remain in their owning panels. `SectionHeading`, `BrandMark`, `EmptyState` and `AddressShare` reuse presentation without introducing layout wrappers or native privileges. Existing CSS classes remain the styling contract.

The launcher stores guide navigation visibility in its own localStorage (`chef25.showGuide`), defaulting to visible when absent or unreadable. Settings updates the shared React state immediately after a successful storage write. This UI-only preference is separate from native launch settings and tavern ZIP backups.

The usage guide is a sandboxed cross-origin iframe pointing at the fixed Chef25 document route. It shares the website's translated source, navigation and search. Production frame-src is restricted to the document path; development points at loopback port 25250. No remote capability is added. The launcher validates both origin and frame window for the ready message, and offers retry after a 20-second timeout. The old JSON article API remains a compatibility endpoint for previously released clients.
