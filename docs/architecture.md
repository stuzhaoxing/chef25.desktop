# Architecture

On macOS, the launcher sets the Foundation process name before initializing Tauri/AppKit so an unbundled development executable appears as `25小厨` in the Dock. `Info.plist` also supplies `CFBundleDisplayName` for embedded development metadata and packaged bundles; the build script tracks that file for recompilation.

```text
Trusted launcher (React, main)
   │ fixed Tauri commands
   ▼
Rust service controller ── bundled Node.js ── SillyTavern :selected-port
   │                                             │
   └─ persistent application data                └─ tavern webview (no native capabilities)
```

`service.rs` owns the child process. Startup reads validated launcher-settings.json (default port 25252 in release builds, 25272 in debug builds; legacy mode fields are ignored), reserves the explicitly selected IPv4 wildcard port, prepares a versioned writable runtime, starts a fixed entry point with the selected port and fixed IPv4 listen arguments and enforced private-network whitelisting, then waits for HTTP readiness and a live child. Failure cleans up only that child. Address-in-use errors are surfaced without switching ports, including an EADDRINUSE or the pinned upstream IPv4 port-conflict diagnostic in the fresh child log after the reservation-to-bind race. Other failures are surfaced. User data and config live outside versioned runtimes. Port settings are read-only while running; saving requires an idle service mutex and no live owned child, so startup cannot race a settings write.

`lib.rs` exposes a small command surface and embeds a separate child webview in the main window (Tauri multiwebview feature). The React host synchronizes its bounds and hides it when navigating to launcher pages, preserving the tavern session. Capabilities and native command guards identify the trusted launcher webview, not the shared OS window. Its main-frame navigation is restricted to the current owned loopback origin, including the selected port. A stale child webview is recreated when the origin changes. The renderer cannot choose executable paths or arbitrary arguments.

`runtime.lock.json` is the source of truth for upstream provenance; update the matching Rust revision constant and displayed version in the same PR. macOS ships one Universal installer, with both architectures in the Rust launcher and Node.js executable. Windows ships one x64 installer. The source archive is checked before extraction. npm dependencies are installed from upstream's lockfile with lifecycle scripts disabled.

Node.js archives are downloaded from the official distribution and verified against committed SHA-256 values. macOS combines the two official Node executables with lipo and ad-hoc signs the result. The pinned SillyTavern dependencies are JS/WASM-only; preparation rejects native modules until an explicit cross-architecture strategy is added. The release job replaces the development signature with Developer ID signing (including Node JIT entitlements), refreshes the Node hash, notarizes and staples both app and DMG, and checks the extracted updater archive.

Website and desktop remain independent repositories. The website reads a small public release manifest; installers and updater artifacts reside in immutable R2 object keys behind a Pages Functions custom subdomain on Workers Free. The bucket remains private; the gateway performs at most two R2 reads per request and has no origin fallback. Uploads stop before the bucket exceeds 9 GB; this is not an account-wide billing cap. No production host credentials are stored here.

`updates.rs` serializes update checks/installations, accepts commands only from the trusted launcher, and uses the pinned Tauri updater to verify payload signatures and signed versions. Downloads complete before the owned service is stopped. The process controller blocks new starts during installation. Update errors release operation guards, and user data remains outside the installed application.

The release publisher uploads and verifies all R2 objects before publishing `updater.json` with separate macOS CPU aliases pointing to the same Universal archive and one Windows x64 installer. Both release manifests use no-store caching. Manual downloads remain exactly two installers. Private signing credentials live in protected GitHub environments, never in source or logs.

The website proxies only the small latest/updater manifests from R2 with no-store caching and redirects versioned download paths to the custom domain. Existing updater endpoints remain compatible. The original disk-backed Caddy configuration is retained until R2 migration is complete. See [R2 rollout](r2-distribution.md).

The download gateway uses Pages advanced mode, with all paths handled by the Function and no installer static assets. The main domain keeps its external authoritative DNS; only the download CNAME targets the Pages project. Preview environments have no R2 binding and downloads disabled.

The launcher uses a viewport-height shell with independently scrollable navigation and launcher pages. Service controls remain in the sidebar; an About entry opens a native HTML modal dialog containing branding, versions and updates. The update panel stays mounted while the dialog is closed to preserve automatic checks and download state. Successful checks report the available version to the launcher, which shows a text badge beside About until a successful check reports no update; failed checks preserve the last known availability. Opening About hides the child tavern webview and closing it restores its visibility without changing the selected page or session; the active tavern host fills the remaining width and height without launcher headers or footers. The initial window is a compact 860 × 640 logical pixels. A running transition requests native window maximization (not fullscreen) through a launcher-only command. A stopped transition exits fullscreen and maximization, then restores and centers 860 × 640, bounded by the current monitor work area (subject to the existing 720 × 620 minimum). An existing fullscreen/maximized choice is preserved when entering the tavern; polling and navigation between pages do not repeatedly resize the window.

`ChefMascot.tsx` owns the launcher-only SVG mascot. Pointer coordinates drive bounded gaze and expression springs without React renders per frame; visibility, unmount and reduced-motion changes stop animation appropriately. The chef artwork and implementation are original; interaction concepts were referenced from [grokbot-web](https://github.com/Coiggahou2002/grokbot-web), with no imported code, geometry or dependency.

The launcher GuidePanel embeds the website's `/guides/sillytavern/` usage documentation in a sandboxed iframe. Production uses `https://www.chef25.com`; development uses the local website on port 25250. The frame has no native capability. Documentation is maintained in the website's content sources and updated by deploying the website. The retired article API, its Vite proxy and its production CSP connection allowance have been removed.

`storage.rs` provides launcher-only, read-only directory listing and bounded UTF-8 previews (128 KiB). Commands derive the root from app_data_dir, reject non-relative paths and link/reparse-point traversal, and verify canonical containment. File content renders as escaped text, never HTML. Browsing runs on blocking workers and does not require the tavern service.

Reset is a launcher-only fixed command. It requires an exact confirmation phrase, holds the service mutex, rejects running services and update installation, and reserves the configured port to reject possible orphaned services. It deletes only fixed owned data entries (the saved launch port in `launcher-settings.json` is kept), rejects linked root ancestors, and never follows nested symlinks during deletion. The UI requires the service to be stopped and uses a modal text confirmation; partial failures are surfaced.

Closing the main window prevents native close and minimizes it to the Dock / taskbar without shutting down or cancelling the owned service. The macOS Dock icon remains visible. The tray is created during setup; failure aborts startup. Left-clicking the tray icon, its Show menu item, a second launch or macOS Reopen unminimizes, shows and focuses the existing window. The tray Quit item calls app.exit(0), sharing system quit cleanup. The settings page has no exit section. ExitRequested and Exit run idempotent shutdown. Shutdown sets a permanent cancellation flag before acquiring the child mutex, interrupts readiness polling, and rejects queued starts. Startup rechecks cancellation after runtime preparation. The owned Node service preloads `native/launcher-lifetime.mjs` and holds a private stdin pipe to the launcher. Forced launcher termination (including a Tauri dev rebuild) closes that pipe: the child sends itself SIGTERM for upstream cleanup, then exits within three seconds if cleanup stalls. The preload preserves upstream arguments and does not modify vendored files. Unknown port owners are never killed.

The running sidebar exposes a Mobile Access entry that opens a responsive modal with LAN/remote modes, locally generated QR codes, copyable URLs and credentials, interface selection and no-address feedback. Opening it hides the native tavern webview, and closing restores it without resetting the session. Connection polling and pending requests stay mounted while closed; revealed passwords are masked on close. The native embedded tavern continues to use loopback. Service startup listens on 0.0.0.0 and forces upstream whitelist mode, with process-local SILLYTAVERN_WHITELIST allowing loopback and RFC1918 IPv4 ranges; Docker host expansion is disabled. Persistent config and user authentication are preserved. The UI explains trusted same-network access; public access is separately opt-in through the protected Cloudflare Tunnel ingress described below. Stopping removes mobile access information and terminates the same owned server.

`backup.rs` implements ZIP format version 1 with a marker and an explicit content allowlist (`data`, config, launcher settings, logs). Launcher-only commands own native file selection; no renderer-supplied arbitrary filesystem write path or additional tavern capability is exposed. Export writes a private temporary ZIP before publishing to the selected destination outside app data. Import rejects traversal, symlinks, special files, case collisions, malformed settings, unsupported markers, and archives over 100,000 entries / 10 GiB unpacked; CRC is checked while extracting to a same-volume staging directory. Old owned entries are moved aside only after full validation; rename failures roll back, retaining recovery folders if rollback fails. Runtime copies are cleared. Process mutex and port reservation serialize both transfers against starts, resets, settings changes and updater installation. Exact confirmation phrases are enforced in both UI and Rust. Replacement is rollback-capable for ordinary I/O failures, not a crash-atomic multi-directory transaction; interruptions may require manual recovery from the retained staging/previous directories.

The Contact Developer section expands inline inside About using native details/summary, with no second modal. About hides the tavern child webview while open. The section embeds the support QR locally and opens the fixed project Issues URL through a launcher-only native command with no renderer-supplied URL or shell input. The update section uses one state-dependent action (check or download), followed by inline installation confirmation and progress.

`managed_remote.rs` creates a persistent random installation credential and browser password in `private-remote/` (Unix 0700/0600), outside backup/reset and denied by native storage browsing. Corrupt/unreadable credentials fail rather than silently changing identity. The native launcher calls `http://127.0.0.1:25250/api/remote/` in debug builds (including dev packages), and the fixed `https://www.chef25.com/api/remote/` API in release builds, with no fallback between environments. It uses that installation credential; it never receives account-level Cloudflare credentials. A device hash determines a unique single-label `r-<hash>.chef25.com` hostname. The backend keeps its logical binding while deleting actual DNS/tunnel resources on release. The website deployment guide describes PostgreSQL reservations, account-wide 1,000 cap, conservative free DNS cap, reconciliation and the independent expiry reaper.

`remote.rs` validates connector tokens (base64 JSON, account ID, tunnel UUID and a base64 secret of at least 32 bytes, including managed 64-byte secrets) and downloads pinned SHA-256-verified official cloudflared assets. The remote process owns the allocated lease before token validation, so validation failure releases it through normal cleanup. It recreates the executable from verified download bytes at every start. `service.rs` owns gateway and connector under service/remote lock order. The bundled Node gateway binds an ephemeral **loopback gateway** port, without changing the manually selected tavern port. That actual gateway port is the sole allowed cloud route; a final route returns 404. The gateway authenticates before forwarding, strips forwarded/IP/auth headers, flushes headers and pipes SSE without buffering. Upgrades are rejected.

Remote access requires an explicit request for each tavern session. Startup never provisions a tunnel and ignores legacy private-remote/enabled files; no auto-connect preference is read or written. Failure is shown in remote status and leaves the tavern usable. Connections keep renewing while the service runs, independently of panel visibility or window hiding; explicit disable or service stop/update/shutdown closes both children. A native heartbeat runs every 30 seconds independently of UI polling, checks owned processes, and closes access after continuous renewal failure (90-second threshold, plus timer/HTTP delay). It scopes cleanup to the current lease ID so an old worker cannot close a replacement. Stop/start-failure cleanup closes local ingress first and asynchronously releases the lease; the server's 150-second lease plus durable reaper handles crashes and failed requests. Cleanup failures remain occupied rather than freeing capacity early. A first client download, API provisioning and DNS propagation can delay readiness.

Connector tokens use `run --token-file` in a private temporary directory, never arguments or user backups. Explicit empty config and a cleared environment prevent unrelated cloudflared config/TUNNEL_* overrides. Readiness sends no browser password and requires this gateway's marker and 401 over HTTPS before sharing. Platform/account administrators remain trusted because control-plane routing can change targets. The browser password is generated and stored only on the installation; the backend stores the hash of its separate device credential. Forced termination cannot guarantee connector/temp-file cleanup, but stdin closure exits the gateway and server lease expiry reclaims the resource. Real account/domain activation, phone networks, Windows execution and packaged acceptance remain unverified.

Transient operation feedback uses the shared `message` API and one `MessageViewport` at the React root. A manual popover places notifications in the top layer; the viewport moves into the active modal to stay within its accessible, interactive boundary. Both the viewport and its grid rows explicitly size to content, and each compact notice fits its text within the available width. Messages have no close button, auto-dismiss (4 seconds, 6.5 seconds for errors), pause on hover/focus, and deduplicate active messages with a three-message limit. Polling failures notify once until recovery. Loading indicators, empty states and destructive-action explanations remain contextual.
Remote access request/stop failures and status-read errors stay inline beneath the action button with an accessible alert. Action failures persist across status polls until the next attempt; a 404 from the allocation API explicitly reports that the service is not yet available.

When the separate native tavern webview is visible, messages stay at the top of the launcher sidebar to avoid being covered by that native surface; other pages and modal dialogs use the window top center.

Shared launcher UI lives in `src/components/`: `Button` / `IconButton` retain native attributes and default to non-submit buttons; forms opt into `type="submit"`. `Dialog` synchronizes controlled state with native modal visibility and keeps children mounted, while `ConfirmationDialog` shares phrase validation, busy dismissal protection and action layout for reset/import/export. Business commands and concurrency guards remain in their owning panels. `SectionHeading`, `BrandMark` and `EmptyState` reuse presentation without introducing layout wrappers or native privileges. Existing CSS classes remain the styling contract.

The launcher always shows the Chinese documentation navigation entry. Settings has no guide visibility control, and the former localStorage visibility preference is no longer read or written.

The usage guide is a sandboxed cross-origin iframe pointing at the fixed Chef25 document route. It shares the website's translated source, navigation and search. Production frame-src is restricted to the document path; development points at loopback port 25250. No remote capability is added. The launcher validates both origin and frame window for the ready message, and offers retry after a 20-second timeout.

Development uses tauri.conf.dev.json with identifier com.chef25.desktop.dev and product/window name 25小厨 Dev. Tauri derives the single-instance lock and app_data_dir from this separate identifier. Production data is not migrated or shared. The remote gateway uses an OS-assigned loopback port. Root dev.sh probes only the website and Vite ports and never kills listeners.

The running sidebar owns remote access and shares one address/QR surface between LAN and remote modes. A launcher-only `remote_capacity` command posts to the fixed capacity endpoint without installation credentials. The server caches provider inventory and failures for 60 seconds under the allocator lock, counting current durable reservations on every query. The most constrained tunnel/DNS usage reports idle below 80%, busy from 80%, and full at 100%; errors remain unknown. Allocation still reconciles fresh inventory and enforces hard limits.

Remote readiness first uses system DNS. After repeated failures, it resolves only the validated allocated single-label device hostname with Cloudflare public DNS (1.1.1.1), checking the random transaction ID, response/question and bounded DNS wire-format message and temporarily pins the returned matching public IPv4 answers in its verification client. This does not modify OS/router DNS, change the shared URL, send the browser password, follow redirects, or disable certificate/hostname/401/gateway-marker checks. DNS answers and request durations are bounded; propagation is retried within the existing lease readiness window.

The remote dialog displays shared tunnel/DNS occupancy and the platform's rolling Cloudflare management API usage as progress bars only while remote access is enabled. While the dialog is open in remote mode, Desktop queries every 15 seconds without overlapping requests, and refreshes after start/stop. The server returns fresh PostgreSQL API usage (1,200 calls per five minutes, no reserved allowance) alongside inventory cached up to 60 seconds. Capacity queries use the cached inventory and database, so polling does not call Cloudflare on every refresh. Unknown inventory is shown explicitly even when API usage is available; transport failures clear the displayed snapshot. These counts exclude chatting, phone page refreshes and lease renewal. They represent this platform's calls, not independently observed account-wide usage.

Remote status polling runs only while the mobile dialog is open, schedules the next read after completion and discards reads started before a start/stop operation. Native lease heartbeats remain independent of UI polling. File browsing memoizes filtering/sorting and reuses a Chinese numeric collator.
